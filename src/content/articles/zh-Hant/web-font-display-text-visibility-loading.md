## font-display控制的是哪一段等待？

頁面已取得文字，畫面卻先空白，再突然換成另一種字，不一定是正文靠JavaScript才出現。網頁字型還在下載時，瀏覽器可能依顯示策略等待或先用備援字型。font-display處理的是這段等待與替換，不會讓字型檔本身變小；應先辨認現象，再選適合閱讀需求的做法。

![抽象字母在透明板上由模糊轉為清晰](../../../assets/articles/web-font-display-text-visibility-loading/zh-Hant-hero.webp)

MDN與CSS Fonts文件將字型使用的時間軸分成阻擋、替換及失敗等階段。瀏覽器需要某個字型時，若它尚未就緒，可能先保留不可見的備援文字，也可能將備援字型畫出來。

所以請求回傳成功、字型下載完成與文字首次可讀，不是同一個時間點。驗收需要看載入過程，不只檢查最後字體是否漂亮。

## block與swap，為何各有代價？

前者給予一段等待字型的機會，文字可能短暫不可見；後者以很短的阻擋期先顯示備援，字型稍後到達仍可能替換。具體時間與瀏覽器行為有關，不宜替所有裝置寫固定秒數保證。

閱讀型頁面通常很在意內容及早可見，但替換時字寬改變，也可能使段落重新排版。選擇應同時看可讀時間與切換後的穩定性，不能只拿其中一項宣布全面改善。

## fallback與optional是否表示完全不下載？

不能這樣簡化。前者提供短的替換機會，後者不提供後續替換期；它們決定字型如何被使用，並不是所有網路情況下都不會有請求的開關。自動策略則由瀏覽器決定。

若採較保守的切換方式，第一次訪問可能留在備援外觀。品牌字體是否一定要在當次出現、是否能接受差異，要由產品與閱讀目標共同決定。

## 備援字型要看中文，不只看英文範例

同一套備援在英文標題上看起來接近，換成繁體中文正文，換行、標點和粗體感受可能不同。還要確認字元覆蓋：某些字仍由其他字型補上時，整段外觀可能不是單一檔案能解釋。

可以挑長標題、數字、常用標點與實際文章測試。字型載入策略不是字形品質的替代品，減少空白後仍須確認讀者能清楚閱讀。

## font-display應寫在一般文字樣式裡嗎？

對單一下載字型的設定，放在相應的字型宣告中，而非只加到段落選擇器。以下是說明結構的示例，路徑並非已部署資產：

```css
@font-face {
  font-family: "ArticleText";
  src: url("/fonts/article-text.woff2") format("woff2");
  font-display: swap;
}
```

實際還須符合字重、樣式與檔案內容。建置工具或外部樣式服務可能另有輸出，編輯器中加了一行，不代表正式頁已採用。

## 先確認請求原因，再考慮預載

如果字型很晚才被樣式引用，需要看發現時間；如果下載本身較久，則另看檔案與交付。預載可以在特定情況提早提供線索，但不能把每個字重與所有字型都預載，期待自動變快。

Chrome開發者資料也提醒，過度預載可能影響其他載入。每次調整保留對應的資源與觀察，不把請求數增加當成改善證據。

## 冷快取、失敗和實際閱讀都要驗收

比較沒有字型快取與已有快取的訪問，記下網路、裝置和網址。再看字型請求失敗時，文字是否仍可讀，備援外觀是否可接受；不能只測一次已快取的重新整理。

版面位移也需要另看，尤其多行標題、按鈕與靠近點擊位置的文字。這篇提供檢查方法，沒有宣稱網站已改動、效能已提升或搜尋排名因此改善。

## 常見問題

### 用系統字型就一定比較好嗎？
不一定。它可以減少某些下載依賴，但字形、品牌需求與跨裝置呈現仍有取捨，應對照實際內容決定。

### 改完設定，為何還看到舊字型？
先確認正式部署與實際取得的樣式，再查快取、字元覆蓋及選中的字型。不要只從最後畫面，推定設定沒有生效或一定是CDN問題。

字型效能要同時回答讀者何時看見文字，以及之後會不會突然換行。把font-display、備援設計與真實載入條件一起驗收，才能知道設定解決了哪一段等待。
