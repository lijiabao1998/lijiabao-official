同一個網址搬遷需求，可能看到 301、302、307 或 308。它們都能指向另一個位置，卻不是只差「永久」與「暫時」。當原請求帶著 POST 資料，或轉址回應被瀏覽器與 CDN 快取時，選錯狀態碼可能讓後續行為和預期不同。先釐清請求方法、目標用途與快取政策，再決定如何發布規則。

## 先判斷搬遷是永久還是暫時

301 和 308 表達資源有新的永久位置；302 和 307 表達暫時移往其他位置。以網站文章改網址為例，已確定舊路徑永久改到新路徑，可以考慮伺服器端永久轉址；若只是短期測試，應依實際情況使用暫時轉址。[Google 搜尋中心說明](https://developers.google.com/search/docs/crawling-indexing/301-redirects)，永久轉址是新網址可能成為標準網址的訊號；暫時轉址不會以相同方式提供該訊號，但仍可能受到其他標準化訊號影響。

## 301 與 302 的歷史行為要注意

[HTTP 語意規範 RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4)指出，由於歷史相容性，使用者代理在跟隨 301 或 302 時，可能把原本的 POST 改成 GET。這不等於所有客戶端都一定會改，也不表示 GET 請求會變成 POST。若轉址發生在表單、付款或 API 寫入流程，應以實際客戶端和伺服器的整段互動測試，確認送往新位置的方法及請求內容是否符合設計。

## 307 與 308 保留原本的方法

307 是暫時轉址，308 是永久轉址；規範要求使用者代理自動跟隨時不可改變原請求方法。也就是說，POST 不應因這兩種轉址自動變成 GET。這不代表目標端一定接受該請求，也不保證所有舊型客戶端都支援相同做法。若目的就是把提交後的使用者帶到可讀取的結果頁，應另外評估 303 的語意，而不是只看網址會不會改變。

## 快取期限不是由永久兩個字決定

301 和 308 在規範中屬於可啟發式快取的狀態碼；實際是否儲存、保存多久，仍受回應標頭、請求條件與快取實作影響。302 和 307 也可能在符合條件並帶有適當快取資訊時被儲存。不要把暫時轉址理解成永遠不會被快取，也不要假設修改來源規則後所有瀏覽器與 CDN 立即更新。測試階段可明確設定合適的 Cache-Control，並確認各層實際回應。

## 檢查 Location 與轉址鏈

瀏覽器收到轉址時，Location 指向的目標必須正確；同時檢查協定、網域、路徑及查詢參數是否按需求保留。從舊網址到最終頁面逐跳觀察狀態碼，避免 A 指向 B、B 又回到 A 的循環。轉址可能發生在應用程式、反向代理或 CDN，多層規則都要檢查。不要只看最終畫面有沒有開啟，也要記錄中間每一跳。

例如舊文章的查詢字串可能用於追蹤或頁面功能，轉址後是否保留，應由網站需求決定，而不是一律刪除或不加判斷地轉送。若目標來源不同，還要確認網址中沒有不應暴露的參數；設定規則時只使用必要資料，測試紀錄也避免留下真實使用者的憑證。

## 發布前後用真實請求驗證

先在測試環境準備不含個資的範例，分別觀察 GET 與需要支援的 POST，確認最終伺服器收到的方法、資料與授權行為。涉及跨網域時，還要檢查憑證、Cookie、CORS 與敏感資料傳遞的設計；不同用戶端可能有不同限制。上線後以安全的測試資料確認狀態、標頭和目標內容，並檢查是否被舊快取影響，避免靠反覆提交真實交易測試。

## 搜尋結果與成功轉址是兩件事

HTTP 回應正確，並不等於搜尋引擎已更新索引。Google 可以跟隨轉址，永久轉址提供標準化訊號，但最終收錄與搜尋呈現仍由多個因素決定。更新內部連結和網站地圖指向預期網址，並透過 Search Console 觀察；不要把一次 200 或一次索引請求視為排名保證。

選擇轉址碼時，同時確認位置是否永久、方法能否改變、快取如何更新，以及搜尋系統如何理解。把每一層的實際回應測出來，才能知道規則是否真正符合網站用途。
