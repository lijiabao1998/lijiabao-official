## bfcache 保留的是哪一種瀏覽狀態

正式站已更新，直接開啟能看到新段落，按上一頁卻回到原先畫面。這個現象值得查，但不能立即宣布 CDN 沒更新。瀏覽器的 bfcache 可能恢復先前頁面與其狀態，觀察起點和重新發出 HTTP 請求不同。先記下實際操作，再決定應查部署、回應還是頁面恢復流程。

![瀏覽器視窗、返回箭頭與分開的網路回應卡片呈現頁面恢復概念。](../../../assets/articles/bfcache-history-navigation-http-cache/zh-Hant-hero.webp)

MDN 與 web.dev 將這種最佳化與一般 HTTP 回應快取區分：符合條件的頁面離開後可被保留，返回時有機會直接恢復。這能改善往返速度，卻不表示每次上一頁都必然使用。瀏覽器、頁面特性與當時條件都可能影響結果，不能以速度很快或表單內容還在，單獨證明本次來源。本文說明排查方法，沒有宣稱已替任何網站變更策略或完成實測。

## 同一個網址，也可能經過不同回來方式

先分別記錄直接開啟、重新整理、由另一頁按返回的結果。即使地址列一樣，這些動作也不宜被記成完全相同的測試。對照具辨識度的正文、觀察時間與路徑，不只看首頁圖片或頁籤標題。若有語言、轉址或登入狀態差異，也先標明，避免把不同條件的畫面混在一起，得到看似矛盾的結論。

## 看見舊畫面，先保留兩種待確認

一種可能是新網路回應本身仍舊，另一種是原頁面被恢復，尚未重新取得需要更新的資料。也可能另有應用程式狀態或服務工作者等因素，因此這個區分只是起點。先查實際請求與瀏覽器觀察，不把上一頁結果直接歸咎於某一層。若來源提交與部署都還沒核對，也要保留建置未含新內容的可能，不急著清除全部快取。

## pageshow 讓恢復事件有觀察入口

MDN 說明，pageshow 可在初始載入與歷史返回等情境觸發；事件的 persisted 值可協助辨認從保留頁面恢復的情況。應在合適測試環境設計必要觀察，不把監測程式任意貼到正式客戶頁面。一次事件不是完整應用狀態報告，仍需對照目前網址、操作與要更新的資料。開發工具的暫時觀察，也不等於已為所有使用者部署相同處理。

## bfcache 恢復後，哪些資料值得重新確認

像庫存、預約名額或目前帳號狀態，可能比靜態文章段落更需要即時確認。這是依用途決定的應用設計，不代表每次 bfcache 恢復都應整頁重載。先定義資料可以舊到什麼程度，再選擇合適更新方式；取得資料失敗時，也讓使用者知道尚未更新，不能保留舊數字卻宣稱已同步。畫面顯示與伺服器端授權仍各自需要正確處理。

## 登出後的畫面，不是權限驗證的替身

測試可以使用不含個資的帳號資料，觀察登出後再返回會顯示什麼，以及後續受保護請求是否仍由伺服器正確拒絕。即使畫面立即消失，也不能只靠這一點證明整套權限安全。反過來，歷史畫面仍可見值得處理，卻不能從截圖直接推論伺服器仍允許操作。敏感資訊、顯示策略與存取控制應一起評估，不用一個標頭代替全部設計。

## 開發工具的結果，寫清楚測了哪個環境

Chrome DevTools 提供往返快取的檢查入口，可觀察該環境是否成功恢復及可能阻礙。介面與條件會隨版本改變，依當前說明使用，不把舊文章的障礙清單當成所有瀏覽器永久規則。記錄版本、精確頁面及測試動作，成功就說本次情境成功；沒有成功時保留原因，不為取得綠色結果而刪掉仍有用途的功能。

## 交付可重現的差異，不把清除當成唯一答案

有用的紀錄包括哪種操作看到哪個正文、是否發出新請求、事件觀察到什麼，以及後續資料更新是否符合用途。涉及交易，不反覆提交真實付款或訂單來測試返回。只補已確認需要的更新流程，之後再以同樣條件核對。部署證據與使用者返回體驗都保留，後來的人才能知道修的是哪一段，而非只剩一次重整後正常的描述。

排查 bfcache，先辨認頁面如何回來，再判斷哪些狀態要更新。讓部署、HTTP 回應與歷史恢復各有可核對的證據，才不會為一張舊畫面重做整個發布流程。
